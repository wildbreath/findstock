# 连板天梯数据说明

天梯有独立的本地存档。日线下载完成，不代表同一时期的涨停池已经存档。

## 存在哪里

默认文件为项目下 `data/findstock.sqlite3`，可通过 `FINDSTOCK_DB_PATH` 更改。
涨停池保存到 `ladder_snapshot` 表：

| 列 | 保存内容 |
| --- | --- |
| `trade_date` | 交易日期，主键，每天一条 |
| `fetched_at` | 取数时间，数据库列统一使用 UTC |
| `payload` | JSON，含当日完整沪深 A 股涨停列表、原始来源、取数时间和快照状态 |

每只股票包含代码、名称、连续涨停数、股价、涨幅、成交额、换手率、封板资金、首次及最后封板时间、
炸板次数、行业和上市板块。源端没有的可选字段为 `null` 或空字符串，页面显示缺失值。
同一天重新获取成功后会更新该行，较早发出的请求不会覆盖较新的结果。因此这是每日快照存档，
不是每个盘中时刻的版本历史。已有日期没有自动过期删除机制。

## 何时保存、何时读取

- 浏览天梯时，只读取当前可见日期；本地有收盘后存档时直接使用。
- 当日盘中快照最多复用 60 秒；15:10 后再次查询会重新抓取并标记为收盘后快照。
- 初始化及增量任务先扫描近 45 个自然日的缺口，再下载日线。按需任务保存指定的近期日期。
- 失败日期记录到 `meta.ladder_sync_pending_dates:v1`，后续数据更新会重试；已有快照不会被失败或空响应清空。
- 没有页面访问、没有更新任务时，程序不会自行每日运行。盘中自动刷新也仅在页面可见时执行。

`is_final` 表示收盘后抓取，不代表人工逐股确认。交易日缺失与真实“当日零涨停”不能靠空响应区分，
因此程序不把空响应作为完整存档。取数成功会落库，断网或重启之后仍可读取。

## 数据从哪里来

近期优先使用东方财富涨停股池，经 AKShare 的 `stock_zt_pool_em` 获取；其历史查询范围有限，
“本程序尝试最近 45 个自然日”不表示源端承诺保存 45 天。

缺失或更早日期改用同花顺公开历史接口：

- `https://data.10jqka.com.cn/dataapi/limit_up/limit_up_pool`：完整涨停列表，每页最多 200 行。
- `https://data.10jqka.com.cn/dataapi/limit_up/continuous_limit_up`：源端连续涨停梯队。

程序检查请求日期与返回日期、完整分页总数、代码重复、分组数量、连续板数与分组高度、
连续涨停股票是否在股池中，以及封板时间是否属于当天。源端缺少成交额、行业时留空。
`high_days` 的“几天几板”可能含断板，历史标签也存在错位，不用它计算连板数。
连续板取 `continue_num`；完整连续梯队之外的当日涨停股票为首板。

两家来源可能存在股票范围与统计口径差异。JSON 的 `origin=eastmoney/ths` 保存原始来源；
`data_source=local` 只表示这次读取走了本地缓存，不会丢掉 `origin`。旧存档缺少 `origin` 时默认东方财富。
界面标明同花顺来源，板块筛选仍使用当前东方财富行业归属，不代表历史归属。

## 补历史与检查完整性

```powershell
python -m app.cli.ladder --start 2025-10-16 --end 2026-10-16
```

命令限定近一年内已收盘的日期，按照交易日历逐日执行，保留已有收盘后存档，不下载日线。
运行前会把已有天梯导出为 `data/ladder-before-backfill-时间戳.json`。
每次新增后重新读库核对列表内容；结束时再次逐日检查是否存在缺失或非收盘快照。
`data/ladder-backfill-report.json` 保存区间、应有交易日数、新增及复用日期、缺失日期、失败原因与是否通过。
有缺失或失败时进程返回非零退出码，可以重复运行补缺，已经完成的日期不会重新抓取。

该检查能确认日期覆盖、请求结果完整性和落库一致性，不能保证第三方源端本身没有漏股或错数。
不使用日线涨幅阈值伪造历史股池；涨停价格舍入、ST 历史、停复牌、新股制度等都会影响这种重建。

## 备份

天梯补录前的 JSON 备份仅包含天梯，便于保留原始存档，不包含日线、自选股或其他配置。
如需备份整个数据库，应使用 SQLite Backup API；运行中的数据库采用 WAL 模式，
只复制 `.sqlite3` 单个文件可能遗漏尚未写回的数据。备份文件同样需要妥善保存。
